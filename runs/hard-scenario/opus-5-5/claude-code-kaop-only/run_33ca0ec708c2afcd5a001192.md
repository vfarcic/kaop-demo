**Root cause:** the `orders-fastpath` canary Deployment (created 19:03:26Z) gives its pods the label `app=orders`, so the `orders` Service picks them up. Its container is hard-coded to return HTTP 500 (`-status-code=500`). About one in three checkout requests lands on it and fails.

## What is failing
- **Checkout (`storefront` → `orders`) fails partially.** The `orders` Service selector is `app=orders`. It has 3 ready endpoints:
  - `10.244.0.98` and `10.244.0.99` are `orders-574f6fc5b9-*` pods, which are healthy.
  - `10.244.0.104` is `orders-fastpath-8476ddbc8b-nt5qx`, which always returns 500.
- **All pods report Ready.** The bad pod passes its checks because http-echo's 500 is the app's normal response, and `orders-fastpath` defines no readiness probe.

## Evidence
- **`orders-fastpath` spec:**
  - Pod labels: `{"app":"orders","track":"fastpath"}`
  - Args: `["-listen=:8080","-text=order accepted","-status-code=500"]`
  - Annotation: `description: "Canary of the new orders fast path. Not wired into the storefront yet."`, `owner: payments-team`. This claim is false: the shared `app=orders` label wires the canary into the `orders` Service.
- **EndpointSlice for `orders`:** `orders-fastpath-8476ddbc8b-nt5qx` is listed with `ready=true`.
- **ConfigMap `storefront`:** `location / { proxy_pass http://orders:8080; }`. Every request goes through the Service, so traffic is spread across all 3 pods.
- **`shopper` log** (a synthetic checkout loop hitting `http://storefront/checkout`):
  - From 19:00:28 to 19:03:33: only `200`.
  - First `500` at `19:03:35`.
  - Since 19:03:30: 60× `200`, 40× `500` (40%, close to the expected 1 in 3).
- **`storefront` access logs:** both pods show the 500s, e.g. `[19/Oct/2026:19:04:48 +0000] "GET /checkout HTTP/1.1" 500 15`. Pod `2qz2m` logged 22× 200 / 13× 500, pod `xvz2k` 16× 200 / 14× 500. Both nginx pods fail at the same rate, which points downstream of nginx.

## Checked and not related
- **`storefront` rollout to rev 2 (19:04:26):** the only template difference is the annotation `kubectl.kubernetes.io/restartedAt`; image, probe and ConfigMap mount are the same. It is a plain restart, and the 500s started a minute before it.
- **`newsletter` CrashLoopBackOff (6 restarts):** it has failed since creation. Log: `connecting to smtp relay mail.internal:25` / `smtp relay unreachable, giving up`, and its command always ends in `exit 1`. It is not on the checkout path. It is a separate problem: either `mail.internal:25` is unreachable or it is a script that always exits non-zero, and running it as a Deployment means it restarts forever.
- **Other checks:** there are no NetworkPolicies or Ingresses in `shop`. The `orders` rev-1 pods have 0 restarts.

## Fix
Take the canary out of the `orders` Service. Any one of these works (a human applies it):
1. **Fastest:** `kubectl scale deploy/orders-fastpath -n shop --replicas=0`. Alternatively, `kubectl delete deploy/orders-fastpath -n shop`.
2. **Proper fix:** give the canary its own `app` label. The selector can't be changed in place, so recreate the Deployment with `selector.matchLabels` and template labels set to `app: orders-fastpath, track: fastpath`. Also remove `-status-code=500` before it is ever routed traffic.
3. **Alternative:** narrow the Service selector to stable pods only. Add `track: stable` to the `orders` template, wait for the rollout to finish, then run `kubectl patch svc orders -n shop -p '{"spec":{"selector":{"app":"orders","track":"stable"}}}'`. Order matters: patching the Service first would leave it with zero endpoints.

**Verify:** the `orders` EndpointSlice should list only the 2 `orders-574f6fc5b9` IPs, and `kubectl logs -n shop deploy/shopper` should show only `200`.

## Confidence
High. The cluster records the fastpath pod with `ready=true` in the `orders` endpoints, the canary's spec sets `-status-code=500`, and the first 500 came 8 s after that pod became Ready.

What the cluster can't show: who created `orders-fastpath` (only the annotation `owner: payments-team`), and why `storefront` was restarted at 19:04:26.
