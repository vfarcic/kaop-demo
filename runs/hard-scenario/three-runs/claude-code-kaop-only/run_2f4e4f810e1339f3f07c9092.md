**Root cause:** The `orders-fastpath` canary was deployed at 18:45:22Z with pod label `app=orders`. That matches the `orders` Service selector (`app=orders`), so the canary joined the backends that receive real checkout traffic. Its container is configured with `-status-code=500`, so every request routed to it fails. That is about 1 in 3 checkouts.

The canary's own annotation says *"Canary of the new orders fast path. Not wired into the storefront yet."* (owner: payments-team). The cluster shows that claim is false: the canary is serving production traffic.

## Failing component
- **Where customers see it:** `storefront` (nginx) returns 500 on `/checkout`.
- **Where the fault is:** `orders-fastpath-8476ddbc8b-5fc7v` (10.244.0.86), reached through Service `orders`.
- `storefront`, `orders` (stable) and `shopper` are all healthy. No NetworkPolicies exist in the namespace.

## Evidence
- **Service:** `svc/orders` selector is `app=orders`.
- **Endpoints:** EndpointSlice for `orders` holds three ready endpoints: `.80` and `.81` (orders-574f6fc5b9), plus `.86` (`orders-fastpath-8476ddbc8b-5fc7v`).
- **Canary spec:** `orders-fastpath` template has labels `{app: orders, track: fastpath}` and args `["-listen=:8080","-text=order accepted","-status-code=500"]`. Stable `orders` has the same image but no `-status-code`, so it returns 200.
- **Canary logs:** every request gets a 500, from its first request onward:
  `2026/10/19 18:45:28 orders:8080 10.244.0.83:57090 "GET /checkout HTTP/1.1" 500 15 ...`
  `2026/10/19 18:48:31 orders:8080 10.244.0.87:57072 "GET /checkout HTTP/1.1" 500 15 ...`
- **Stable orders logs:** only 200s, e.g. `18:48:29 ... "GET /checkout HTTP/1.1" 200 15`.
- **Storefront access logs:** the 500s are passed straight through from upstream, with matching 15-byte bodies:
  `10.244.0.84 - - [19/Oct/2026:18:48:31 +0000] "GET /checkout HTTP/1.1" 500 15`
- **Shopper probe** (`curl http://storefront/checkout` every 2s):
  - From 18:42:22 to 18:45:26 every request returned 200, apart from a single `000` at pod start.
  - The first 500 was at **18:45:28**, 6 seconds after the canary started.
  - 29 of about 94 requests since then failed (~31%). That matches one bad backend out of three.
- **Timing:** the first 500 at the canary (18:45:28) and at the shopper (18:45:28) are the same second.

## Other findings
- **`newsletter`: CrashLoopBackOff, 6+ restarts.** It is out of the checkout path and unrelated to this incident. Its script logs `connecting to smtp relay mail.internal:25` then `smtp relay unreachable, giving up`, and it ends with an unconditional `exit 1`. So it will crash even when the relay is reachable.
- **Secrets:** no workload in the namespace references a Secret.

## Fix
**Immediate:** take the canary out of the `orders` endpoints.
```sh
kubectl scale deploy/orders-fastpath -n shop --replicas=0
```

**Permanent:** keep canary pods out of the stable selector. A Deployment's selector is immutable, so the canary has to be recreated with a different `app` label:
```sh
kubectl delete deploy/orders-fastpath -n shop
```
Then re-apply it with this change:
```yaml
spec:
  selector:
    matchLabels: {app: orders-fastpath, track: fastpath}
  template:
    metadata:
      labels: {app: orders-fastpath, track: fastpath}
```
Also drop `-status-code=500` before the canary is ever intentionally wired into traffic.

The alternative is to label the stable pods `track: stable` and set the `orders` Service selector to `{app: orders, track: stable}`. That needs a rollout of `orders` first.

**Newsletter (separate issue):** remove the unconditional `exit 1`, and make `mail.internal:25` resolvable and reachable.

**Verify:** `kubectl get endpointslice -n shop -l kubernetes.io/service-name=orders` should list only the `orders-574f6fc5b9-*` pods, and `kubectl logs deploy/shopper -n shop --tail=20` should show only 200s.

## Confidence
**High.** Selector overlap, canary args, the 500s in the canary's logs, the matching start times and the ~1/3 failure rate all point the same way.

- Who ran the 18:46 ConfigMap apply and storefront restart, or why.
